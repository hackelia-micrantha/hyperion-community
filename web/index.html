Engineering in practice

Public reference evidence and internal engineering scope are distinguished below. Internal source is not part of the Community distribution; implemented configuration does not imply runtime qualification.

Cloud infrastructure

Public: OpenTofu reference modules for infrastructure and Incus, validated without live provisioning.

Internal: Infrastructure definitions for AWS, Azure, DigitalOcean and local virtualization (Libvirt and Incus); provider and runtime qualification varies.

Host automation

Public: Ansible and K3s bootstrap with non-mutating defaults and checksum-verified installation.

Internal: Environment-aware host provisioning and cluster configuration.

Kubernetes and GitOps

Public: Hardened Kubernetes workloads, Kustomize overlays and immutable Flux source patterns.

Internal: Shared workload definitions with environment-specific reconciliation.

Infrastructure security

Public: Restricted Pod Security, default-deny networking, threat modeling and publication leakage checks.

Internal: SOPS/age and Ansible Vault secret management, with deployment credentials separated from routine CI.

Reproducible CI/CD

Public: Read-only, commit-pinned CI, shared mise tasks, schema validation and security scanning with Trivy and Checkov.

Internal: Locked Nix toolchain and daemon-free compliance; isolated rootless role testing is still being qualified.

Software supply-chain security

Public: Digest-pinned example images, exact tool versions and publication provenance review.

Internal: Default-deny registry admission policy separates package trust, pull authorization and image provenance. Runtime acceptance is separate.

Observability

Internal: GitOps-managed Loki and Fluent Bit configuration for resource-bounded, cluster-local logging. Storage is ephemeral; durable retention and recovery are not yet qualified.

Developer and operator experience

Public: Consistent mise workflow and documented ownership boundaries.

Internal: Nix-based tooling and a read-only Hyperctl prototype. Public CLI packaging and broader lifecycle commands remain planned.

Current maturity: Hyperion is running internally on Dubnium. The public Community edition is a reference implementation with automated source validation; independent runtime and recovery qualification remain outstanding. See the draft source-alpha notes; no release has been published.

Architecture and trade-offs

Layered ownership. OpenTofu/Terraform defines infrastructure, Ansible handles bootstrap, Kubernetes defines workloads, and Flux provides the intended reconciliation boundary. Read the architecture overview.

Explicit effects. The verification path operates on synthetic inputs, not live infrastructure. The public Incus example checks the provider schema without planning or applying changes.

Portable infrastructure. Use common infrastructure automation across cloud providers and local virtualization without requiring every workload to run on Kubernetes. Provider-specific lifecycle qualification remains separate.

Application and infrastructure separation. Applications own their builds and releases; the platform is evolving toward explicit infrastructure lifecycle ownership and independently reviewed deployment configuration.

Bounded authority. Public CI is read-only and does not need private deployment credentials. The public repository is independently inspectable without access to private operational source.
